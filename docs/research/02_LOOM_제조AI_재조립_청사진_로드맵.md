## 0. 결론 먼저

1. **제품 정의** — LOOM은 "**질문 하나에 근거와 함께 답하고, 사람이 승인한 판단을 기록하며, 그 기록으로 다음 판단이 나아지는**" 제조 운영 지능 스택이다. E8의 5개 제품(NFLOW Ai·NDX Cloud·NDX Pro·NAXiS·NAX Ops)과 R&D 에이전트 과제를 **11개 섹터**로 분해해 다시 조립했다.
2. **E8 기능 커버리지** — E8 공개 기능 **129개**를 전수 추출해 섹터에 매핑했다(§4). 여기에 E8에는 없고 이상적인 제조 AI에 필요한 **LOOM+ 기능 24개**를 더했다(§5).
3. **시작점 판단** — **"척추(Spine)" = S0 공통 계약 → P 가상 실증공장 → S2 연결 → S3 온톨로지 → S6 근거 질의**부터 시작한다. E8는 물리 엔진(아래)부터 10년에 걸쳐 올라왔지만 지금 가치의 중심을 온톨로지(위)로 옮기고 있다. 후발 개인 빌더는 **가치의 중심부터 들어가 아래 계층을 오픈소스로 붙이는** 순서가 맞다(§7).
4. **첫 번째 수용 기준** — 가상 프레스-용접 라인에 결함 원인을 **정답이 알려진 채로** 심어 두고, "어제 2라인 용접 불량이 늘어난 원인은?"이라는 질문에 **근거 경로(불량→LOT→스테이션→설비→정비이력→파라미터 변화)와 데이터 버전을 함께** 답하게 한다. 주입 시나리오 20개 중 원인 1순위 정답 **14개 이상**.
5. **일정** — PRISM 캘린더를 건드리지 않는 기본안(A)에서는 이번 주 Stage 0, **11/17부터 Stage 1 척추 본체**다. 11월 커리어 포트폴리오 창을 우선하는 대안(B)은 척추를 9/22로 당기고 PRISM 스파이크를 미룬다. **이 선택만 본인 결정으로 남긴다**(§9).

## 1. 제조 AI의 이상점 — LOOM이 지향하는 상태

### 1.1 E8에서 가져오는 네 개의 믿음

| E8의 표현 | LOOM의 설계 원칙 | 구현 장치 |
|---|---|---|
| "센서 감지와 설비 제어는 자동화됐지만 **이해와 결정은 여전히 사람 몫**" | **P1. 자동화가 아니라 지능화를 만든다** — 감지와 제어 사이의 빈칸(이해·판단)을 채운다 | S3 온톨로지 + S6 근거 질의 + S7 판단 |
| "이상 징후는 AI가 먼저 감지하고, **중요한 판단은 사람이 내린다**" | **P2. 자율 수준을 판단 유형마다 명시한다** — 반복·저위험은 자동, 공정 변경은 승인 | S7 자율 레벨 L0~L3 (§3.4) |
| "어떤 데이터·기준·연산을 거쳐 도출됐는지 **White Box**" | **P3. 근거 없는 답은 답이 아니다** — 모든 응답에 근거 경로·데이터 버전·신뢰도를 붙인다 | S0 provenance + S6 evidence trace |
| "담당자는 바뀌어도 **운영의 기준과 기록은 쌓여** 다음 운영을 만든다" | **P4. 판단은 자산이다** — 질문·근거·결정·승인자·결과를 한 레코드로 남기고 다음 판단의 입력으로 쓴다 | S7 Decision Log + 학습 루프 |

### 1.2 E8에서 가져오되 LOOM이 한 걸음 더 가는 것

| E8의 한계 (분석 문서 §9) | LOOM의 보완 |
|---|---|
| 정량 효과의 근거가 비공개 | **P5. 스스로를 채점한다** — 가상 실증공장에 원인을 알고 주입하므로 RCA 정확도를 수치로 측정한다 (LOOM+ 평가 하네스) |
| 온톨로지 구축이 현장 인터뷰 기반 컨설팅형 | **P6. 스키마를 먼저 고정한다** — 제조 코어 온톨로지(ISA-95 계층 + SOSA/SSN + PROV-O)를 기본 제공하고 확장만 한다. PRISM의 [G][T][P] 3중 스키마와 같은 발상 |
| 제조 양산 라인 데이터가 없어 Proving Plant를 인수로 해결 | **P7. 실증공장을 먼저 시뮬레이션으로 만든다** — SimPy 이산사건 라인 + 공개 데이터셋(SECOM·AI4I·Bosch·MVTec·WM-811K)으로 "데이터가 없어 검증 못 한다"를 개인 수준에서 끊는다 |
| "피지컬AI"가 운영 판단에 머물고 로봇 학습 연계 없음 | **P8. 트윈은 로봇 학습 환경으로 이어진다** — PRISM의 Isaac Lab 익스포트를 S4·S8에 연결 |

### 1.3 이상점 한 장

```
                         ┌──────────────────── 사람 (승인 · 기준 정의) ────────────────────┐
                         │                                                                 │
   감지 ─────► 이해 ─────► 판단 ─────► 예측 ─────► 실행 ─────► 기록 ─────► 학습 ──┐        │
   S2 연결     S3 온톨로지  S7 운영기준  S5 물리      S8 에이전트  S7 결정로그   평가하네스 │        │
   S1 획득     S6 근거질의  S6 RCA      S4 트윈시나리오 (L0~L3)                      │        │
     ▲                                                                              │        │
```

E8 CTO가 제시한 **감지→이해→결정→행동** 루프에 **예측(시뮬레이션)·기록·학습**을 명시적 단계로 넣었다. E8가 "운영이 쌓일수록 진화하는 시스템"이라고 말만 한 부분을 LOOM은 **평가 하네스로 측정 가능한 루프**로 만든다.

### 2.2 척추 — 모든 섹터를 꿰는 단 하나의 규약

**모든 섹터는 같은 Entity ID로 대화한다.** 3D 객체(S4), 센서 시계열(S2), 시뮬레이션 경계조건(S5), 온톨로지 노드(S3), 결정 기록(S7)이 같은 URN을 가리킨다. 이것이 E8가 NDX Pro 3D 객체와 NAXiS 온톨로지를 따로 만들다 뒤늦게 연결하는 비용을 LOOM이 처음부터 피하는 방법이다.

```
urn:loom:{site}:{type}:{local-id}
예) urn:loom:plantA:Equipment:WR-03      용접 로봇 3호기
    urn:loom:plantA:Lot:L20260916-042    LOT
    urn:loom:plantA:Criterion:WELD-STR-01 용접강도 운영기준
```

**하나의 엔티티는 세 개의 면을 가진다** — PRISM [G][T][P] 3중 스키마를 그대로 계승한다.

| 면 | 내용 | 주관 섹터 | PRISM 대응 |
|---|---|---|---|
| **[G] Geometry** | 형상·배치·계층 경로 | S4 · S1 | `scene_node` |
| **[T] Telemetry** | 속성값·시계열·이벤트 (값 + 단위 + 관측시각 + 출처) | S2 | `telemetry.bindings` |
| **[P] Physics** | 물리 파라미터·변동범위·시뮬레이션 경계조건 | S5 | `physics.variation_range` |
| **[S] Semantics** ★LOOM 추가 | 타입·관계·운영기준·문서 연결 | S3 | (PRISM에 없음) |

### 2.3 데이터 모델은 NGSI-LD 모양으로

E8 NAXiS 데모 화면의 데이터 모델 입력 항목은 **ID / Type / Title / Attributes / Unit Code**였고, NDX Pro는 NGSI-LD 준수를 강점으로 내세운다. NGSI-LD의 Property는 `value`·`unitCode`·`observedAt`을, Relationship은 `object`를 갖는다. **LOOM의 엔티티 저장 형식을 처음부터 NGSI-LD JSON-LD 모양으로 두면** 두 제품의 발상을 한 번에 흡수하고, 나중에 표준 브로커와 호환된다.

```json
{
  "id": "urn:loom:plantA:Equipment:WR-03",
  "type": "Equipment",
  "title": "용접 로봇 3호기",
  "tipWear":   { "type": "Property", "value": 0.82, "unitCode": "P1",
                 "observedAt": "2026-09-16T14:05:00Z",
                 "provenance": { "source": "mqtt://line2/wr03", "status": "measured" } },
  "locatedIn": { "type": "Relationship", "object": "urn:loom:plantA:Station:ST-W2" },
  "governedBy":{ "type": "Relationship", "object": "urn:loom:plantA:Criterion:WELD-STR-01" }
}
```

`provenance.status`는 PRISM D-10의 **확인 / 가정 / HOLD**와 같은 값을 쓴다. 모델이 추출한 값은 기본 `가정`이고 사람이 확인해야 `확인`으로 올라간다.

### 2.4 제조 코어 온톨로지 v0 (S3)

| 그룹 | 클래스 | 정렬 표준 |
|---|---|---|
| 공간·설비 | Site · Area · Line · Station · Equipment · Component · Sensor | ISA-95 설비 계층, SOSA/SSN |
| 제품·공정 | Product · Part · BOMItem · ProcessSpec(Recipe) · Parameter | ISA-95, 자동차 BOM |
| 생산 실적 | WorkOrder · Lot · Measurement · Inspection · Defect | ISA-95 운영 모델 |
| 이벤트 | Alarm · Event · MaintenanceRecord · ChangeRequest(ECO) | — |
| 지식 | Document(+Version) · Criterion(운영기준) · Hypothesis(원인 가설) | PROV-O |
| 판단 | Question · Answer · EvidencePath · Decision · Approval · Outcome | PROV-O |
| 예측 | Scenario · SimulationRun · SurrogateModel · Prediction | — |
| 사람 | Person · Role · Responsibility(담당 구역) | PRISM F-106/107 |

핵심 관계: `partOf` · `locatedIn` · `feeds`(공정 흐름) · `measures` · `produces` · `hasDefect` · `suspectedCause`(신뢰도 포함) · `governedBy` · `documentedIn` · `derivedFrom`(계보) · `supersedes`(버전) · `approvedBy` · `simulates`

> **개인업무용 보안 원칙** — 회사 데이터는 LOOM에 넣지 않는다. 집에서는 가상 실증공장·공개 데이터로 만들고, 회사에는 **방법(스키마·프롬프트·평가 하네스)**만 옮긴다. 회사 PC에서 쓸 때는 LiteLLM을 사내 허용 LLM 또는 로컬 Ollama로만 향하게 한다. 이 원칙이 E8가 강조한 "데이터 주권·온프레미스"를 개인 수준에서 지키는 방법이다.

## 7. 어느 단계부터 시작할 것인가

### 7.1 후보 비교

| 기준 (가중치) | A. 물리부터 (E8가 걸어온 길) | B. 3D 트윈부터 | **C. 척추부터 (S2·S3·S6)** | D. 운영부터 (S7) |
|---|---|---|---|---|
| 다른 섹터가 의존하는가 (×3) | 낮음 — 결과를 붙일 곳이 없다 | 중간 — 객체는 있으나 의미가 없다 | **높음 — 모든 섹터가 엔티티를 참조한다** | 낮음 — 판단할 대상 구조가 없다 |
| 개인업무 적용 (×3) | 낮음 | 낮음 | **높음 — 품질 분석·문서 자동화** | 높음 |
| 입문 코딩 난이도 (×2) | **매우 높음** (수치해석 + GPU) | 중간 (PRISM에서 진행 중) | 중간 (SQL·Python·LLM) | 중간 |
| 컴퓨팅 비용 (×1) | 높음 (GPU) | 낮음 | **낮음 (로컬 LLM 가능)** | 낮음 |
| 커리어 포트폴리오 신호 (×2) | 중간 | 중간 | **높음 — 온톨로지·RAG·에이전트는 2026 채용 키워드** | 중간 |
| E8 가치 중심과의 거리 (×2) | 멀다 (E8도 떠나는 중) | 중간 | **가깝다 (NAXiS·NAX Ops)** | 가깝다 |
| 교육·자기학습 일정 정합 (×1) | 낮음 | 높음 (PRISM 스파이크) | **높음 — 교육 5과정·Phase 5와 겹침** | 중간 |
| **가중 평균 (5점 척도)** | 1.5 | 3.0 | **4.6** | 3.2 |

> 채점(1~5, 기준 순서대로) — A: 1·1·1·1·3·2·2 / B: 3·2·3·4·3·3·5 / C: 5·5·3·4·5·5·4 / D: 2·4·3·4·3·4·3. 가중치 합 14로 나눈 값. 난이도·비용은 **쉬울수록·쌀수록 높은 점수**다.

### 7.2 판정 — C. 척추부터

**근거 1 — 의존의 방향.** 3D 객체, 센서값, 시뮬레이션 결과, 결정 기록은 모두 "무엇에 대한" 것이다. 그 "무엇"을 정의하는 곳이 S3다. E8가 NDX Pro(3D)와 NAXiS(온톨로지)를 따로 만든 뒤 2026년에야 한 흐름으로 묶고 있는 비용이 바로 순서의 비용이다.

**근거 2 — 가치의 방향.** E8는 13년간 물리 엔진 → 트윈 → 온톨로지로 올라왔고, 2026년 모든 발표·영상·신제품이 온톨로지와 에이전트에 있다. 후발 개인 빌더는 **가치가 이동한 곳에서 시작해 아래 계층은 오픈소스(XLB·PhysicsNeMo·PRISM)로 붙인다.**

**근거 3 — 본인에게 맞는 입구.** 제조 현장 7년의 경험이 가장 직접 들어가는 곳이 온톨로지 설계와 운영 기준 정의다(E-NXS-17 "현장 인터뷰 기반 운영 로직"을 인터뷰 없이 본인이 채울 수 있다). 코딩은 입문이지만 척추는 SQL·Python·LLM 호출 수준에서 시작할 수 있고, 가장 어려운 물리 계층을 뒤로 미룬다.

**근거 4 — 스스로 채점할 수 있는 첫 목표.** Stage 1의 수용 기준은 정답지를 가진 가상 실증공장 위에서 **숫자로 판정**된다. "잘 된 것 같다"로 끝나는 데모가 아니다.

**단, 물리(Stage 4)는 Stage 0에만 의존하므로** GPU 여건이 생기거나 흥미가 크면 Stage 2·3과 병렬로 당겨도 설계가 깨지지 않는다.
